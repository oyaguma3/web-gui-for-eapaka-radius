# 画面仕様

- 状態: 初版の画面をすべて記載（2026-10-08。初版のステップ4）。セッションの画面、監査ログの provisioning-api のタブ、ダッシュボードのセッション数を追加（2026-10-09。Provisioning API 0.3.0）。eapaka-node-provisioner 経由のときの画面を追加（2026-10-10。§11。設計概要 §12）
- 関連: [設計概要](design-overview.md)（アカウントと権限、セッション、Provisioning API との連携）
- 作法は aka 版（web-gui-for-aka-only-server）の画面仕様にそろえる。

## 1. 共通

### 1.1 レイアウト

- 上部のナビゲーションに、ダッシュボード、加入者、RADIUSクライアント、認可ポリシー、セッション、操作の記録（eapaka-node-provisioner 経由のときだけ。§11）、監査ログ（管理者のみ）、アカウント（管理者のみ）と、ログイン中のユーザーID のメニューを出す。画面幅が狭いときは項目の並びを複数行に回す。
- パスワードの変更待ちの間は、ユーザーID のメニュー以外を出さない。
- ユーザーID のメニューには、アカウントの種類、パスワード変更（最初の管理者以外）、ログアウトを出す。
- 下部に BFF のバージョンを出す。
- 日時は BFF のタイムゾーン（`TZ`）で `2006-01-02 15:04:05 JST` の形で出す。

### 1.2 ログインと権限

| 状態 | 通常の画面遷移 | htmx の操作 |
|---|---|---|
| 未ログイン、セッション切れ | ログイン画面へ移動する（303）。元のパスを `next` に入れる | 401 と `HX-Redirect` でログイン画面へ移動する |
| パスワードの変更待ち | パスワード変更画面へ移動する | 403 と `HX-Redirect` でパスワード変更画面へ移動する |
| 権限のない画面・操作 | 403 のエラー画面 | 403 のエラー画面 |

- ログイン後の移動先（`next`）は、同じサイトの絶対パスだけを使う。それ以外は `/` にする。
- 別のサイトからのフォーム送信は 403 で拒否する（`CrossOriginProtection`）。
- セッションの Cookie は `__Host-eapaka-webgui-session`（Secure、HttpOnly、SameSite=Strict、有効期限なし）。Cookie はポートを区別しないので、同じホストで動かす aka 版（`__Host-aka-webgui-session`）とは別の名前にしている。

### 1.3 操作の結果

- 変更の操作は htmx で送り、画面の該当部分（`#accounts`、`#subscriber`、`#clients`、`#client`、`#policy`）だけを差し替える。結果は部分の先頭に出す。
- 削除の後は一覧の画面へ移動し、削除したことを出す。
- 削除はブラウザの確認ダイアログを出してから行う（`hx-confirm`。キャンセルすれば送らない）。
- 入力の誤りでフォームを出し直すときは、パスワード以外の入力を残す。
- 入力の誤りなどは 4xx、処理の失敗は 5xx で、説明つきの HTML を返す。htmx は既定では 4xx / 5xx の応答を差し替えないので、`htmx-config` の `responseHandling` で差し替えるようにしている。
- htmx の操作で権限エラーなどのエラー画面を返すときは、本文（`main`）全体をエラーの表示に置き換える（`HX-Retarget` / `HX-Reswap`）。
- 本PoCの Admin TUI と同時に使った場合など、対象が他の操作で削除されていた（404）・既に登録されていた（409）ときは、その旨が分かる文（「他の操作（本PoCの Admin TUI など）で削除された可能性があります。」など）を出す。詳細の画面や削除で 404 になったときは、一覧へのリンクを添える。
- Provisioning API に接続できない・エラーを返したときは 502 で説明を出す（接続できないときは原因の見当。設計概要 §7.1）。

### 1.4 秘密の値

- Ki / OPc と共有シークレットは、詳細の画面のボタンを押したときだけ Provisioning API から取得して表示する（管理者のみ）。他の操作で該当部分を差し替えたり、画面を移動したりすると表示は消える。
- 取得は provisioning-api の監査ログと BFF の監査ログに残る。BFF のログや監査ログに値は出さない。
- 入力欄（加入者の登録の Ki / OPc、RADIUSクライアントの共有シークレット）は伏せずに表示する。入力の誤りでフォームを出し直すときは、入力を残す（パスワードは残さない）。

## 2. ログイン（`/login`）

- 誰でも開ける。ログイン済みなら `next`（なければ `/`）へ移動する。
- 入力: ユーザーID、パスワード。

| 結果 | 表示 |
|---|---|
| 成功 | `next` へ移動する。パスワードの変更待ちなら、パスワード変更画面へ移動する |
| ユーザーID かパスワードが違う（存在しない ID を含む） | 401「ユーザーID またはパスワードが違います。」 |
| 失敗が続いてロック中 | 429「ログインの失敗が続いたため、このユーザーID では一時的にログインできません。しばらくしてからやり直してください。」 |

- 既定では、5 回続けて失敗すると、最初の失敗から 15 分の間ロックする（`EAPAKA_WEBGUI_LOGIN_MAX_FAILURES`、`EAPAKA_WEBGUI_LOGIN_LOCK_DURATION`）。ロック中は正しいパスワードでもログインできない。
- ログアウトはメニューのボタン（`POST /logout`）で行い、ログイン画面へ移動する。

## 3. パスワード変更（`/password`）

- 管理者と一般ユーザーが使える。最初の管理者には 403 で「`.env` で変更してください」と出す。
- 入力: 現在のパスワード、新しいパスワード、新しいパスワード（確認）。
- 他人が設定したパスワードでログインしている間は、「続けるには、パスワードを変更してください。」と出し、この画面以外を使わせない。
- 成功したら `/password?done=1` へ移動して完了を出す。他の端末のセッションは無効になる。

| 誤り | 表示 |
|---|---|
| 確認用と一致しない | 「新しいパスワードと確認用のパスワードが一致しません。」 |
| 現在のパスワードが違う | 「現在のパスワードが違います。」 |
| 規則に合わない | 「パスワードは 8 文字以上にしてください。」など |
| 現在と同じ | 「現在と同じパスワードは使えません。」 |

## 4. アカウント管理（`/accounts`）

- 管理者（最初の管理者を含む）だけが使える。

### 4.1 一覧

| 項目 | 内容 |
|---|---|
| ユーザーID | |
| 種類 | 最初の管理者 / 管理者 / 一般ユーザー |
| 作成 | 作成日時と作成者。最初の管理者は「.env」 |
| 状態 | パスワードの変更待ちなら「パスワード変更待ち」 |
| 操作 | 操作できるアカウントにだけ出す（「操作」を開くと出る）。パスワードの再設定（新しいパスワードと確認）と削除 |

- 最初の管理者を先頭に、残りはユーザーID の順に並べる。
- 操作できるのは、最初の管理者なら管理者と一般ユーザー、管理者なら一般ユーザー。
- パスワードを再設定すると、そのアカウントのログイン中のセッションは無効になり、次のログインでパスワードの変更を求める。

### 4.2 作成

- 入力: ユーザーID、種類（作成できる種類だけを選択肢に出す）、初期パスワード、初期パスワード（確認）。
- ユーザーID は Provisioning API の `X-Operator-Id`（操作者）になるので、その形式（英数字と `.` `_` `@` `-` の 64 文字まで）に限る。
- 作成したアカウントは、最初のログインでパスワードの変更を求める。

| 誤り | 表示 |
|---|---|
| ユーザーID の形式 | 「ユーザーID は 1〜64 文字の英数字と . _ @ - で指定してください。」 |
| 既にある（最初の管理者の ID を含む） | 409「そのユーザーID は既に使われています。」 |
| 確認用と一致しない、規則に合わない | パスワード変更と同じ |
| 権限がない種類 | 403「この操作の権限がありません。」 |

## 5. ダッシュボード（`/`）

- ログインしたユーザーなら誰でも開ける。
- Provisioning API の `/status` から、加入者数、RADIUSクライアント数、認可ポリシー数、セッション数、ノード名、provisioning-api のバージョンと起動日時を出す。セッション数は provisioning-api 0.3.0 以降だけが返すので、返さなければセッションの欄を出さない。
- Provisioning API に接続できないときも画面は返し、原因の見当（設計概要 §7.1。クライアント証明書の未登録、サーバー証明書の不一致や SAN の不足、名前解決や接続の失敗など）を出す。
- 加入者・RADIUSクライアント・認可ポリシー・セッションの件数は、それぞれの一覧へのリンクにする。

## 6. 加入者

### 6.1 一覧（`/subscribers`）

- 全員が使える。IMSI の前方一致（15 桁までの数字）で検索し、50 件ずつ表示する（「次のページ」「先頭へ」）。総数を出す。
- 項目: IMSI（詳細へのリンク）、SQN、AMF、登録日時。
- 削除の後は「加入者 … を削除しました。」を出す。同じ IMSI の認可ポリシーが残っていれば、そのことと認可ポリシーへのリンクを添える。

### 6.2 登録（`/subscribers/new`）

- 全員が使える（一般ユーザーが Ki / OPc を扱えるのは、この入力中だけ）。
- 入力: IMSI（15 桁）、Ki、OPc（16 進 32 桁）、AMF（16 進 4 桁、既定 8000）、SQN（16 進 12 桁、既定 000000000000）。16 進は大文字でもよく、小文字にして送る。
- `?imsi=` で IMSI を入れた状態で開ける（認可ポリシーの画面の「加入者を登録」から使う）。
- 登録したら詳細へ移動して「加入者を登録しました。」を出す。

| 誤り | 表示 |
|---|---|
| 形式 | 項目ごとに「IMSI は 15 桁の数字で入力してください。」「Ki は 16 進 32 桁で入力してください。」など |
| 既にある | 409「その IMSI の加入者は既に登録されています（本PoCの Admin TUI など、他の操作で登録された場合もあります）。」 |

### 6.3 詳細（`/subscribers/{imsi}`）

- 全員が使える。SQN、AMF、登録日時、この加入者のセッションの一覧（§9）へのリンクと、同じ IMSI の認可ポリシーの有無（あれば既定の動作とルールの件数、認可ポリシーの画面へのリンク。なければ「作成する」のリンク）を出す。
- 認可ポリシーがあれば「状態」の行に状態と、停止・再開のボタンを出す（§8.3。全員が使える）。結果はこの詳細の画面に出す。
- 管理者には次を出す。
  - Ki / OPc の表示（ボタン。§1.4）
  - 認証パラメーターの変更: Ki、OPc（入力したときだけ送る）、AMF、SQN（値が変わったときだけ送る。SQN を送らなければ、認証で進んだ SQN に触れない）。変更した項目を「AMF を変更しました。」のように出す。変わった項目がなければ「変更はありません。」
- 削除は全員ができる。確認ダイアログに「同じ IMSI の認可ポリシーは削除されません。」と出す。

## 7. RADIUSクライアント

### 7.1 一覧と登録（`/clients`）

- 全員が一覧を見られる。全件を IP アドレスの順に出す。項目: ID、IP アドレス（詳細へのリンク）、名前、ベンダー。
- 管理者には登録のフォームを出す。入力: IP アドレス（IPv4。各数の先頭に 0 を付けない）、共有シークレット（空白なしの印字可能 ASCII 1〜128 文字）、名前（英数字と `_` `-` の 1〜64 文字）、ベンダー（任意。英数字・空白・`-` の 64 文字まで）。ID はサーバーが採番する。
- 同じ IP アドレスが既にあれば 409。

### 7.2 詳細（`/clients/{id}`）

- 全員が見られる。項目: ID、IP アドレス、名前、ベンダー。
- 管理者には次を出す。
  - 共有シークレットの表示（ボタン。§1.4）
  - 設定の変更: IP アドレス・名前・ベンダー（値が変わったものだけ送る）、共有シークレット（入力したときだけ送る）。IP アドレスを変えても ID は変わらない。他のクライアントが使っている IP アドレスには変えられない（409）。
  - 削除（確認ダイアログ）

## 8. 認可ポリシー

### 8.1 一覧（`/policies`）

- 全員が使える。IMSI の前方一致で検索し、50 件ずつ表示する。項目: IMSI（編集へのリンク）、状態（利用中 / 停止中。停止中と不明な状態は赤字。状態のない Provisioning API では「-」）、既定の動作、ルールの件数。
- 「開く・作成する」: IMSI（15 桁）を入れると、その IMSI の編集画面へ移動する（`/policies/open?imsi=`）。なければ新しく作る画面になる。

### 8.2 編集（`/policies/{imsi}`）

- 全員が使える（認可ポリシーの作成・変更・削除は一般ユーザーもできる）。
- 同じ IMSI の加入者の有無を出す。なければ「本PoCには登録されていません」（接続方式01 の加入者のように、鍵を aka-only-server が持つ場合は認可ポリシーだけでよい）と、加入者の登録へのリンクを出す。
- まだ保存していない IMSI では「この IMSI の認可ポリシーはまだありません。「保存」で作成します。」を出す。既定は deny、ルールなし（Admin TUI と同じ）。
- 入力:

| 項目 | 内容 |
|---|---|
| 既定の動作 | deny（拒否）/ allow（許可）。どのルールにも一致しないときの動作 |
| ルール（複数） | NAS-ID（空白なしの印字可能 ASCII 253 文字まで。`*` はすべて）、許可する SSID（1 行に 1 つ。32 バイトまで。`*` はすべて。前後の空白と空行は除く）、VLAN ID（0〜4094。空なら割り当てない）、Session-Timeout（0〜86400 秒。空か 0 なら送らない） |

- ルールは上から順に評価する。各ルールに「上へ」「下へ」「削除」のボタン（先頭の「上へ」と末尾の「下へ」は押せない）、末尾に「ルールを追加」のボタンを出す。追加したルールの NAS-ID は `*`。
- ルールの追加・削除・並べ替えと既定の動作の切り替えは、フォーム全体を `POST /policies/{imsi}/edit` に送り、操作を施した編集欄を返してもらう（htmx で差し替える。Provisioning API には送らない）。このとき「保存していない変更があります。「保存」で反映します。」を出す。
- 「保存」で全体を置き換える（`PUT /policies/{imsi}`）。既定の動作が allow のときは、保存の前に確認ダイアログ（「既定の動作が allow です。どのルールにも一致しない接続も許可します。保存してよろしいですか？」）を出す（Admin TUI と同じ警告）。成功したら「作成しました。」「保存しました。」を出す。
- 入力の誤りは、保存の前に BFF で確かめ、該当するルールの項目の下に出す（「2 行目の SSID が長すぎます（32 バイトまで）。」など）。Provisioning API が返した `invalidParams`（例 `rules[0].allowedSsids[1]`）も、該当するルールの項目に対応付けて出す。
- 保存済みのものは削除できる（確認ダイアログ）。加入者は削除しない。
- 保存済みのものは、加入者の上に「状態」と停止・再開のボタンを出す（§8.3）。停止・再開では、編集中のフォームも一緒に送り、保存していないルールの変更はそのまま残す（保存はしない。「停止・再開しても、保存していないルールの変更はそのまま残ります（保存はしません）。」と添える）。保存（全体の置き換え）では状態は変わらない（保存のボタンの説明に添える）。

### 8.3 停止・再開

- 全員が使える。認可ポリシーの状態を変える（`PUT /policies/{imsi}/status`）。停止中の加入者の認証は、鍵の置き場所によらず本PoCが拒否する。効くのは次の認証からで、接続中のセッションは切れない。
- 表示: 「利用中」と「停止する」のボタン、または「停止中（認証を拒否します）」（赤字）と「再開する」のボタン。Valkey を直接書き換えた不正な値は「不明な状態（値）（認証を拒否します。停止または再開で正しい状態に戻せます）」と両方のボタン。状態のない応答（0.3.0 以前の provisioning-api、0.2.0 以前の provisioner）では「接続先が停止・再開に対応していません（本PoCの provisioning-api 0.4.0 以降（provisioner 経由では、eapaka-node-provisioner 0.3.0 以降も）で使えます）。」と出し、ボタンを出さない。
- 確認ダイアログ: 「加入者 … を停止します。次の認証から拒否します（接続中のセッションは切れません）。よろしいですか？」「加入者 … を再開します。次の認証から認可ポリシーのルールに従います。よろしいですか？」
- 完了: 「停止しました。次の認証から拒否します（接続中のセッションは切れません）。」「再開しました。次の認証から認可ポリシーのルールに従います。」
- 認可ポリシーが他の操作で削除されていたら 404「IMSI … の認可ポリシー は登録されていません。他の操作（本PoCの Admin TUI など）で削除された可能性があります。」provisioner 経由の 409（同じ IMSI の操作が処理中、完了していない操作がある）は §11.1 と同じ文とリンク。
- BFF の監査ログに「加入者の停止」「加入者の再開」として残る（provisioning-api・provisioner の監査ログも同じ名前で出す）。

## 9. セッション（`/sessions`）

- 全員が使える。provisioning-api の `GET /sessions` から、アクティブセッション（RADIUS の認証で作られ、Accounting-Stop か有効期限で消える）を接続開始の新しい順に 100 件まで出す。見出しに総数（「アクティブセッション 全 3 件」）を出し、100 件を超えるときは「接続開始の新しい 100 件だけを表示しています。IMSI で絞り込んでください。」を出す。
- `?imsi=`（15 桁）でその加入者のセッションだけを出す（見出しは「IMSI … のアクティブセッション 2 件」。「すべてのセッションを表示」で戻る）。形式が違えば 400「IMSI は 15 桁の数字で入力してください。」（Provisioning API には送らない）。
- 項目: 接続開始、IMSI（加入者の詳細へのリンク）、NAS（NAS-Identifier と IP アドレス）、端末の IP アドレス、通信量（入力 / 出力。`1.5 MiB` のように単位をつけ、マウスを重ねると octets の値）、Acct-Session-Id、セッションID（Class 属性の UUID）。値がないものは `-`。
- 端末の IP アドレス、Acct-Session-Id、通信量は、NAS から Accounting-Request を受けるまで空であることと、有効期限（24 時間。Accounting-Request を受けるたびに延びる）を注記する。
- 読み出しだけで、セッションの切断はできない。provisioning-api の監査ログにも残らない。
- 0.3.0 より前の provisioning-api では 502「本PoCの Provisioning API がセッションの参照に対応していません（provisioning-api 0.3.0 以降が必要です）。」

## 10. 監査ログ（`/audit`、`/audit/prov`）

- 管理者だけが使える。上部のタブで「BFF」（`/audit`）と「provisioning-api」（`/audit/prov`）を切り替える（eapaka-node-provisioner 経由のときは「provisioner」「aka-only-server」のタブも出す。§11.6）。どちらも新しい順に 50 件ずつ出す（「さらに古いものを表示」で続きを読み込む）。

### 10.1 BFF（`/audit`）

- BFF の監査ログ。項目: 日時、操作者、操作元（接続元のアドレス）、操作、対象、内容（JSON）。
- 記録する操作: ログイン（成功・失敗）、アカウントの作成・削除、パスワードの再設定・変更と、BFF を通した Provisioning API の操作（加入者の登録・変更・削除、Ki / OPc の表示、RADIUSクライアントの登録・変更・削除、共有シークレットの表示、認可ポリシーの保存・削除）。
- Provisioning API の操作の内容には、トレースID（`trace_id`）と、変えた項目の名前などを入れる（秘密の値は入れない）。provisioning-api の監査ログ（§10.2、本PoCのホストの `provisioning-api.log`）の `trace_id` と突き合わせられる。

### 10.2 provisioning-api（`/audit/prov`）

- provisioning-api の監査ログ（`GET /audit-logs`）。Provisioning API を通した変更操作と、Ki / OPc・共有シークレットの取得。BFF 以外の管理クライアントの操作も含む。本PoCの Admin TUI での操作は含まない。
- 項目: 日時、操作者（`X-Operator-Id`。ない操作は `-`）、管理クライアント（本PoC側の `PROVISIONING_API_ADMIN_CLIENTS` の識別名）、操作（BFF の監査ログと同じ名前。認可ポリシーは作成と変更に分かれる）、対象（加入者・認可ポリシーは IMSI、RADIUSクライアントは ID）、内容（provisioning-api が記録した変更内容。秘密の値は含まない）、トレースID。
- 保持する件数には上限があり（本PoC側の `PROVISIONING_API_AUDIT_MAX`。既定 10000 件）、それより古いものは本PoCのホストのログファイルにあることを注記する。
- 続きの位置（`?before=`）の形式が違えば 400「続きの位置の指定が正しくありません。」（Provisioning API には送らない）。0.3.0 より前の provisioning-api では 502「本PoCの Provisioning API が監査ログの参照に対応していません（provisioning-api 0.3.0 以降が必要です）。」

## 11. eapaka-node-provisioner 経由のとき

設定 `EAPAKA_WEBGUI_ADMIN_API=provisioner` のときの画面（設計概要 §12）。ここに書いていない画面（RADIUSクライアント、セッション、アカウント等）と、§1 の共通の作法は、直接つなぐときと同じ（provisioner が Provisioning API と同じ形で中継する）。

### 11.1 共通

- ナビゲーションに「操作の記録」（§11.5）を出す。
- 接続できない・エラーの文は「provisioner に接続できません。」「provisioner がエラーを返しました。」などにする（原因の見当は provisioner 向けの文。設定 `PROVISIONER_ADMIN_CLIENTS`、`server-cert`、共有ネットワーク `eapaka-provisioner` など）。
- provisioner の先の下流に接続できないときは 503「provisioner から aka-only-server に接続できません。ダッシュボードで接続の状態を確かめてください。」など。書き込みの途中で失敗して元に戻したときは「途中まで行った変更は元に戻しました。」を添える。
- 次のエラーには、その操作の記録（§11.5）へのリンク「操作の記録を開く」を添える。
  - 409（同じ IMSI に完了していない操作がある）「同じ IMSI に完了していない操作が残っています。「操作の記録」で、その操作をやり直すか閉じてから、もう一度操作してください。」
  - 500（途中で失敗し、元に戻せなかった）「aka-only-server への操作が途中で失敗し、元に戻せませんでした。provisioner が後で自動でやり直します。「操作の記録」で状況を確かめてください。」
- 409（同じ IMSI の操作が処理中）「同じ IMSI の操作が処理中です。少し待ってから、もう一度操作してください。」
- 加入者の登録・変更・削除と、操作の記録のやり直し・閉じるのフォームには、表示のたびに作るキー（隠し項目 `idem`）を持たせ、`Idempotency-Key` として送る。同じフォームを送り直しても二重に処理されない。provisioner に届かなかった（接続できない・タイムアウト）ときは同じキーを残し、provisioner が断った（4xx）ときは新しいキーにする。
- 1 回の呼び出しの上限は 60 秒（直接のときは 10 秒）。

### 11.2 ダッシュボード（`/`）

- provisioner の `/status` から、本PoCの Provisioning API と aka-only-server への接続（加入者数、版、ノード名。接続できなければ provisioner が返す原因の見当。aka-only-server を扱わない設定ならその旨）、未完了の操作の件数、provisioner の版と起動日時、鍵の置き場所（PLMN マップ）、vector-gateway の AVクライアント（ない・無効ならその旨）、provisioner の Valkey への接続を出す。
- 未完了の操作があれば「完了していない操作があります（実行中 …、やり直し中 …、失敗 …）。」と操作の記録へのリンクを先頭に出す。
- RADIUSクライアント・認可ポリシー・セッションの件数は出さない（provisioner の `/status` にない）。
- provisioner に接続できないときも画面は返し、原因の見当を出す。

### 11.3 加入者の一覧（`/subscribers`）

- 鍵の置き場所が本PoCのものと aka-only-server のもの、鍵だけ・認可ポリシーだけの IMSI を、IMSI の順に 50 件ずつ出す。総数は出さない（provisioner が返さない）。
- 項目: IMSI（詳細へのリンク）、鍵の置き場所（本PoC / aka-only-server）、SQN、AMF（鍵がなければ「鍵なし」）、認可ポリシー（既定の動作とルールの件数。なければ「なし」）、状態（§8.1 と同じ。認可ポリシーがなければ「-」）、食い違い（§11.4 の表の名前）。
- 一覧では、鍵を本PoCに置く加入者について aka-only-server 側を調べないことを注記する。
- 削除の後は「加入者 … を削除しました（認可ポリシーも削除しました）。」

### 11.4 加入者の登録・詳細

- 登録（`/subscribers/new`）: §6.2 の入力に、認可ポリシーの既定の動作（deny / allow。既定 deny）を加える。認可ポリシーはルールなしで加入者と一緒に作り、ルールは登録後に認可ポリシーの画面で編集する。
  - 既定の動作を切り替えると、フォームを描き直す（`POST /subscribers/new/form`。入力は残し、provisioner には送らない）。allow のときだけ、登録の前に確認ダイアログ「認可ポリシーの既定の動作が allow です。どのルールにも一致しない接続も許可します。登録してよろしいですか？」を出す。
  - 鍵の置き場所は選ばせず、provisioner の PLMN マップ（例「00102 → aka-only-server。それ以外の PLMN は本PoC」）を説明に出す（provisioner の状態の写しを 1 分使い回す）。
  - 既にあれば 409「その IMSI は既に登録されています（本PoCの鍵、認可ポリシー）（本PoCの Admin TUI など、他の操作で登録された場合もあります）。」のように、あった場所を出す。
  - 登録したら詳細へ移動して「加入者を登録しました（認可ポリシーも作りました）。」
- 詳細（`/subscribers/{imsi}`）: 鍵の置き場所、SQN、AMF、登録日時（aka-only-server の加入者は、SQN の増加タイプ、平文HTTP での払い出し、許可するクライアントID、変更日時も）、認可ポリシーの概要（認可ポリシーの画面へのリンク）、セッションへのリンクを出す。鍵がなければ「なし」。認可ポリシーがあれば「状態」の行に状態と停止・再開のボタン（§8.3）を出す。
  - 食い違い（`issues`）があれば、先頭に名前と説明・対処を出す。

| 食い違い | 名前 | 説明・対処（要旨） |
|---|---|---|
| `KEY_MISSING` | 鍵がありません | 認証できない。認可ポリシーだけが残っている場合は、削除してから登録し直す |
| `POLICY_MISSING` | 認可ポリシーがありません | 本PoCは認証を拒否する。認可ポリシーを作成する |
| `KEY_IN_OTHER_STORE` | 置き場所でない方にも鍵があります | PLMN マップの一致、Admin TUI などでの登録を確かめ、要らない方を削除する |
| `AV_CLIENT_NOT_ALLOWED` | vector-gateway の AVクライアントを許可していません | aka-only-server の管理 GUI などで許可するクライアントに加える |
| `OTHER_STORE_UNREACHABLE` | 置き場所でない方を確かめられませんでした | ダッシュボードで接続の状態を確かめる |

- 管理者には、鍵があるとき Ki / OPc の表示（§1.4）と「鍵の属性の変更」を出す。§6.3 の項目に加え、aka-only-server の加入者は SQN の増加タイプ（inc1 / inc32 / inc33）と平文HTTP での払い出しの許可を変えられる。変わった項目だけを送り、「SQN の増加タイプ、平文HTTP の許可 を変更しました。」のように出す。鍵がない加入者は 409「この加入者には鍵がないため、変更できません。…」。
- 削除は全員ができる。確認ダイアログに「認可ポリシーと、鍵の置き場所（aka-only-server）の Ki / OPc を削除します。」と出す。途中で失敗して加入者を読み直せないときも、元の失敗の文と操作の記録へのリンクを出す。
- 認可ポリシーの画面（§8.2）の「加入者」は、鍵があれば「登録あり」、なければ「鍵（Ki / OPc）が登録されていません」（認可ポリシーだけでは認証できないこと、登録するには認可ポリシーを削除してから「加入者の登録」で一緒に登録することを添える）。

### 11.5 操作の記録（`/operations`、`/operations/{id}`）

- 閲覧は全員、やり直す・閉じるは管理者だけ。
- 一覧: 完了していない操作（実行中・やり直し中・失敗）を作成の古い順に 100 件まで。タブで状態を絞り込む（`?status=running|retrying|failed`）。件数と、項目（作成日時（詳細へのリンク）、操作（加入者の登録・変更・削除）、IMSI、鍵の置き場所、状態、やり直した回数、次のやり直し、操作者）を出す。補償・自動のやり直し・「失敗」の意味を注記する。
- 詳細: 操作の ID、IMSI、状態、やり直した回数、操作者と管理クライアント、作成・更新日時、トレースID と、手順ごとの状態（手順の名前、下流、状態、最後の失敗）。完了したものも 7 日間見られる。なければ 404「操作の記録が見つかりません。完了した操作の記録は 7 日で消えます。」
- 管理者には「手での対応」として次を出す。
  - 「やり直す」（失敗のときだけ）: 続きをその場で 1 回行う。完了すれば「やり直しました。操作は「完了」になりました。」、また失敗すれば「やり直しましたが、また失敗しました。provisioner が自動でのやり直しを再開します（24 時間）。」
  - 「閉じる」（やり直し中・失敗のとき）: 確認ダイアログを出してから閉じる。「操作を閉じました。」
- 鍵の変更が反映されたか分からない変更（変更の記録が失敗で、鍵の変更の手順が未実施のもの）は、「鍵の変更が反映されたかどうか分かりません」と対処を出し、「やり直す」を出さない（provisioner も受け付けない）。
- 一般ユーザーには「やり直しと閉じるは、管理者が行います。」を出す。

### 11.6 監査ログ

- タブは「BFF」「provisioner」（`/audit/provisioner`）「provisioning-api」「aka-only-server」（`/audit/aka`）。provisioner が aka-only-server を扱わない設定なら「aka-only-server」のタブは出さない（provisioner の状態の写しで決める）。
- provisioner（`/audit/provisioner`）: provisioner の監査ログ。項目: 日時、操作者、管理クライアント（自動のやり直しは `-`）、操作（「自動のやり直し」「操作のやり直し」「操作を閉じる」を含む）、対象（操作の記録があればリンク）、結果（完了・元に戻した・やり直し中・失敗・閉じた）、内容（「名前: 値」を並べたもの）、トレースID。
- provisioning-api（`/audit/prov`）: provisioner が中継する provisioning-api の監査ログ。provisioner を通した操作の管理クライアントは provisioner の識別名になる。
- aka-only-server（`/audit/aka`）: provisioner が中継する aka-only-server の監査ログ。項目: 日時、操作者、管理クライアント、操作、対象、内容（変更は「amf: 8000 → 9000」の形）、トレースID。
- BFF の監査ログには、加入者の登録・変更の内容に鍵の置き場所（`keyStore`）、登録に認可ポリシーの既定の動作（`policyDefault`）を加え、操作の記録のやり直し・閉じるも記録する（対象は操作の ID）。
